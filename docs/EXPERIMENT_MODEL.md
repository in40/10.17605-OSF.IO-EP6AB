# SymFw — Модель для эксперимента + ось «MoE vs dense»

## Выбор модели для эксперимента
Критерий: модель должна реально проявлять **hijack phenomenon** (устойчиво
следовать системному промпту), иначе сигнал мутный и эксперимент провалится
из-за модели, а не метода.

- **0.8B** — слишком слабая, только для plumbing (уже покрыто mock'ом).
- **2B** — слабо-средне, риск false-negative на методе.
- **4B** — dev sweet-spot: приличное следование, ~8GB fp16, быстрая итерация.
- **8–9B** — лучший сигнал: сильное следование + сильный hijack, более линейно
  разделимые репрезентации (линейная-гипотеза). ~16GB fp16, влезает в 24GB.
  Референс transcript'а = Qwen3-8B.

Жёстко:
- **INSTRUCT/chat-вариант, не base** (base не следует системному промпту → phenomenon'а нет).
- **Проб не переносится между моделями** → экспериментальная модель должна
  совпадать/быть близка к целевой деплоя.

Рекомендация: основная **Qwen3-8B instruct**; для быстрой разработки **4B**,
потом подтвердить на 8B; **0.8B пропустить**.

## MoE — не «больше = лучше» для проба
(напр. Qwen3-30B-A3B)
- Судить по **активным** параметрам (~3B/токен) для силы phenomenon, по **total** для VRAM.
- **Routing = confound**: смесь экспертов → кусочно-линейная, менее гладкая
  геометрия → «ось перехвата» хуже линейно разделима → проб **сложнее**.
- **VRAM по total**: 30B fp16 ≈ 60GB → нужна карта 80GB или offload.
- **Hybrid (Qwen3.5-Next, SWA + recurrent DeltaNet)**: «hidden state на слое L»
  мутнее + проблема KV-reuse → пробинговать сложнее и нестандартно.
- MoE оправдан **только если это целевая модель деплоя** (проб не переносится).

## Ось статьи
**«MoE vs dense для проба»** — AUROC + линейность разделимости vs архитектура/размер —
сделать **отдельной осью** статьи, **не** основной валидацией.
Основная валидация = **dense 8B**.

## Кросс-модельное переиспользование проба (4B → 122B, одно семейство)
- **Сам проб напрямую — НЕТ.** Разные hidden-dim, глубина, геометрия. `w` живёт в
  дельта-пространстве 4B → к дельтам 122B не приложить (размерность + геометрия).
- **Переиспользуется:**
  - размеченный датасет (модель-агностичен — тот же, заново снять дельты);
  - метод/пайплайн (two-pass, нормализация, калибровка) без изменений;
  - затюненные гиперпараметры: `pool`, `d/||e_base||`, `pca_dim`, регуляризация,
    политика порога. **Слои переносятся как доля глубины**, не абсолютный индекс.
- **Обязательно на 122B:** заново снять дельты (дорого — VRAM), переобучить проб
  (дёшево, секунды CPU), заново откалибровать порог и **валидировать**.
- Опционально: проекция 4B→122B (CKA-выравнивание) для warm-start — не стоит того
  против простого переобучения на готовом рецепте.
- Кавэаты: extraction 122B = VRAM-бутылочное горлышко (~244GB fp16 → мульт-GPU);
  если MoE → routing-confound, сигнал мутнее.

**Тезис для статьи:** эксперимент на 4B даёт валидированный рецепт + датасет,
поэтому прогон на 122B — быстрый retrain с готовыми гиперпараметрами, а не с
нуля. Но сам проб — новый, и результат на 122B надо померить, а не перенести на веру.

## Track: влияние квантования на проб (ось статьи)
Гипотеза: квантование возмущает hidden states → размывает линейную разделимость
«оси перехвата» → роняет AUROC проба. Насколько — и есть предмет трека.

Дизайн:
- Один датасет, один рецепт; варьируем **точность**: fp16/bf16 (baseline) vs
  bitsandbytes-4bit (NF4) vs AWQ-Q4 vs GPTQ-Q4.
- Метрики: AUROC, линейная разделимость (маржа / разброс косинусов к оси),
  per-group — особенно FP на tricky.
- Контроль: train и eval **внутри одной точности** (не смешивать).
- Кросс-точность: fp16-проб на квантованных дельтах и наоборот → штраф за
  mismatch (важно, т.к. train/serve должны совпадать).

Ожидаемый результат: квант снижает разделимость; величина падения = **предел
допустимого квантования** для firewall.

Кавэат: AWQ/GPTQ могут не отдавать `output_hidden_states` через `AutoModel` →
трек может упереться в поддержку; bnb NF4 надёжнее.

Ценность: отвечает на вопрос «можно ли вешать firewall на квантовый прод и не
сыплется ли детекция».
